# Story 1.4：7 类嘴型渲染与手动测试

Status: done

## Story

As a 开发者,  
I want 手动触发并观察 7 类数字狗嘴型,  
so that 我能在接入音频前确认每种嘴型视觉差异明确。

## Acceptance Criteria

1. **Given** App 已加载宠物舞台，**When** 开发者触发 `closed`、`small`、`wide`、`round`、`smile`、`teeth`、`pant` 中任一嘴型，**Then** 数字狗嘴巴切换到对应视觉状态，**And** 每种嘴型与其他嘴型有可观察差异。
2. **Given** 当前处于手动嘴型测试，**When** 切换任一嘴型，**Then** 当前嘴型标签同步更新，**And** 输入来源标记为 `manual` 或开发测试状态。
3. **Given** 手动测试结束，**When** 用户重置到待机，**Then** 嘴型回到 `closed`，**And** 不影响宠物状态机的默认 `idle` 行为。
4. **Given** 本 Story 只负责 7 类嘴型视觉和手动验证，**When** 开发者实现，**Then** 不接入 TTS、示例音频、上传音频、麦克风、真实播放、`LipSyncTimeline` 生成、波形、文本高亮、延迟校准、真实 AI、网络、数据库或新增 Android 权限。
5. **Given** 用户使用 TalkBack 或测试框架读取页面，**When** 切换手动嘴型，**Then** 宠物舞台、调试台和手动测试入口都以可读文字或语义暴露当前嘴型与来源，不能只靠图形差异表达。
6. **Given** 当前环境可运行 Android 构建验证，**When** Story 完成，**Then** `testDebugUnitTest`、`assembleDebug`、`compileDebugAndroidTestKotlin` 和 `lintDebug` 通过；如有 Android 平板模拟器可用，运行 `connectedDebugAndroidTest` 并记录结果。

## Dev Notes

### 当前 Story 目标

本 Story 是 Epic 1 的第四个实施 Story。目标是在现有宠物舞台上落地 `MouthShape` 的 7 类视觉状态，并提供开发手动测试入口，让后续 TTS、示例音频、上传音频、麦克风和调试台时间轴接入前，先确认每种嘴型可观察、可测试、可被 TalkBack / 测试语义读取。

本 Story **不是** TTS、示例播放、上传、麦克风、时间轴生成、播放同步、波形、文本高亮、延迟校准或真实动画 Story。手动测试只改变当前 UI 状态，不代表真实播放链路。

### Story 1.4 需求来源

- Epic 1 Story 1.4 要求手动触发并观察 7 类数字狗嘴型。
- FR9 要求支持 `closed`、`small`、`wide`、`round`、`smile`、`teeth`、`pant`，并且每种嘴型可由手动测试或播放流程触发。
- UX-DR28 / UI-SPEC 规定七种嘴型视觉契约：闭合线、小开口、大开口、圆嘴、咧嘴、露齿/咬合、开心喘气。
- LIPSYNC-SPEC 的手动测试模式要求每个嘴型可单独触发，来源为 `manual`，不需要播放音频，调试台显示当前嘴型和来源。

### 技术要求

- 使用 Kotlin + Jetpack Compose，不新增第三方依赖。
- 口型渲染优先使用 Compose 基础绘制；`Canvas`、`DrawScope`、`drawBehind` 或基础 `Box` 形状均可。
- 渲染器只消费 `MouthShape` 和颜色 / modifier 参数；不得知道输入来源、播放时间、时间轴或 reducer。
- 手动测试入口只发送用户意图，例如 `selectManualMouth(shape)` 和 `resetManualMouth()`；UI 不直接操作音频或未来时间轴。
- 所有新增状态必须通过 `SpeechDemoState` 传递到顶部状态栏、宠物舞台、调试台和竖屏摘要。
- 保持 Story 1.2 / 1.3 的响应式布局、安全区处理、48dp 触控目标和动态语义测试。

### 架构合规要求

- 共享模型放在 `sharedmodel`，状态逻辑放在 `state`。
- 可复用嘴型渲染器优先放在 `dogrenderer`；如果直接服务宠物舞台，也可放在 `petstage`，但应保持独立 Composable，避免把所有绘制塞回 `PetStagePlaceholder`。
- `DigitalDogApp` 可以组合手动测试入口，但不应持有复杂业务逻辑。
- 调试台只读当前状态，不反向驱动宠物表现；手动测试入口应通过根状态更新而不是让调试台私自改字段。
- 不新增第二套 `MouthShape`、`InputSource`、`PetState`、`LipSyncTimeline` 或播放状态模型。

### UI 与嘴型视觉契约

| MouthShape | 中文标签 | 视觉要求 | 使用边界 |
| --- | --- | --- | --- |
| `closed` | 闭合 | 一条柔和闭合嘴线，无开口 | 待机、静音、思考、错误、重置 |
| `small` | 小开口 | 小椭圆或小弧形开口 | 普通短音、默认有声段 |
| `wide` | 大开口 | 纵向明显张口 | 重音、响亮元音 |
| `round` | 圆嘴 | 圆形或椭圆开口 | o/u 类声音 |
| `smile` | 咧嘴 | 横向咧嘴，略带微笑 | e/i 类声音 |
| `teeth` | 露齿 | 轻微露齿或上下咬合 | f/s/v/th 类摩擦音感觉 |
| `pant` | 喘气 | 开心喘气嘴型，可爱但克制 | 结束反馈或宠物表达，不能替代普通发音 |

### 手动测试交互建议

- 入口标题可用 `手动嘴型测试`。
- 七个选项可以用紧凑按钮、两行网格或可换行按钮组。
- 按钮文案建议为 `closed 闭合`、`small 小开口`、`wide 大开口`、`round 圆嘴`、`smile 咧嘴`、`teeth 露齿`、`pant 喘气`。
- 当前选中的嘴型需要在按钮、宠物舞台语义和调试台中都可识别。
- `重置待机` 应把状态恢复为默认 idle/closed，避免用户误以为手动测试是正式播放状态。

### 可访问性要求

### Anti-Patterns

- 不要新增第二套嘴型 enum、字符串列表或手动测试状态模型。
- 不要把手动嘴型测试做成正式音频播放流程。
- 不要实现 TTS、示例音频、上传、麦克风、`TextToSpeech`、`MediaPlayer`、`AudioRecord`、文件选择器、权限请求、网络、数据库或真实 AI。
- 不要创建 `LipSyncTimeline`、`LipSyncSegment`、波形、文本高亮或延迟校准 UI；这些属于后续 Epic 2 / Epic 3。
- 不要使用颜色作为唯一差异；每种嘴型必须有明显形状差异。
- 不要让 `pant` 成为普通语音默认嘴型；它是宠物反馈嘴型。
- 不要用截图像素测试证明嘴型；用模型、语义和调试文本建立稳定测试。
- 不要使用旧 iPadOS / SwiftUI / AVFoundation 方案；所有旧平台表述均已被 Redmi Pad SE / Android 决策覆盖。

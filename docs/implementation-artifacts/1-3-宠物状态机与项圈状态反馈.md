# Story 1.3：宠物状态机与项圈状态反馈

Status: done

<!-- Validation is optional. Run validate-create-story before dev-story when extra quality review is needed. -->

## Story

As a 开发者,  
I want 通过统一状态机驱动数字狗状态和项圈反馈,  
so that 后续 TTS、示例、上传、麦克风和 AI 状态都能复用同一套宠物行为模型。

## Acceptance Criteria

1. **Given** App 已启动，**When** 系统处于默认状态，**Then** `PetState` 为 `idle`，当前嘴型为 `closed`，**And** 顶部状态栏、宠物舞台、项圈状态光和调试台都显示待机状态。
2. **Given** 开发测试入口或 mock 事件可触发状态，**When** 依次触发 `listening`、`thinking`、`speaking`、`done`、`error`，**Then** 顶部状态栏、项圈状态光、宠物舞台状态摘要和调试台状态同步变化。
3. **Given** 状态为 `listening`、`thinking` 或 `error`，**When** UI 渲染当前宠物表现，**Then** 当前嘴型必须保持 `closed`，不得提前实现非闭口嘴型切换。
4. **Given** 状态进入 `done` 或 `error`，**When** 收到恢复到待机的 mock 事件，**Then** 状态回到 `idle`，当前嘴型回到 `closed`，项圈回到低亮待机反馈。
5. **Given** 本 Story 只负责状态机和状态反馈基础，**When** 开发者实现，**Then** 不接入真实 TTS、示例播放、上传、麦克风、音频分析、播放控制、真实 AI、7 类嘴型视觉切换或自动计时动画，**And** 不新增 Android 权限、网络、数据库或新依赖。
6. **Given** 用户使用 TalkBack 或测试框架读取页面，**When** 焦点进入顶部状态、宠物舞台、调试台或调试摘要，**Then** 当前宠物状态、当前嘴型、输入来源和解析质量都以可读文字或语义存在，不能只靠项圈颜色表达。
7. **Given** 当前环境可运行 Android 构建验证，**When** Story 完成，**Then** `testDebugUnitTest`、`assembleDebug`、`compileDebugAndroidTestKotlin` 和 `lintDebug` 通过；若没有真实平板或模拟器，必须在 Dev Agent Record 中记录未执行 `connectedDebugAndroidTest` 和真实 Redmi Pad SE 状态验收的原因。

## Dev Notes

### 当前 Story 目标

本 Story 是 Epic 1 的第三个实施 Story，目标是把 Story 1.2 的静态首屏升级为“由统一状态对象驱动”的宠物舞台。完成后，后续 TTS、示例音频、上传、麦克风和未来真实 AI 都应复用同一套 `PetState` 和状态 reducer，不再各自硬编码状态。

本 Story **不是** TTS、示例播放、上传、麦克风、口型时间轴、7 类嘴型视觉或真实动画 Story。它只建立状态模型、mock 状态事件、项圈状态反馈和 UI 读状态的路径。

### Story 1.3 需求来源

- Epic 1 Story 1.3 要求通过统一状态机驱动数字狗状态和项圈反馈，覆盖 `idle`、`listening`、`thinking`、`speaking`、`done`、`error`。
- PRD FR-3 要求状态机通过数字狗动作和项圈反馈表现状态变化。
- MVP 规格要求第一版保留未来 AI 对话状态，不接真实 AI，且 mock 事件可触发每个状态。
- UI-SPEC 要求项圈状态光对应：`idle` 低亮、`listening` 蓝色、`thinking` 蓝色呼吸语义、`speaking` 珊瑚、`done` 绿色、`error` 黄色。
- LIPSYNC-SPEC 要求静音、待机、思考和错误状态下保持 `closed`；播放中后续才由时间轴驱动嘴型。

### 技术要求

- 使用 Kotlin + Jetpack Compose，不引入新依赖。
- 状态模型和 reducer 必须是纯 Kotlin，适合 JVM 单元测试。
- UI 层只读取状态并发送意图，不直接操作音频、播放、上传、麦克风或 AI。
- 所有后续输入入口最终都应复用 `SpeechDemoState` / `SpeechDemoStore` 或等价单一状态源。
- `PetState` 的英文稳定 ID 使用小写语义：`idle`、`listening`、`thinking`、`speaking`、`done`、`error`，便于后续调试台和 AI adapter 复用。

- 若需要 UI 测试触发不同状态，优先通过 `DigitalDogApp` 参数注入状态，而不是增加正式用户可见的 debug 控件。

### 架构合规要求

- 核心模型放在 `sharedmodel` 或 `state`，状态逻辑放在 `state`。
- `DigitalDogApp` 继续只负责组合根布局、主题和状态注入，不要把 reducer 逻辑写进 Composable 内部。
- `PetStagePlaceholder` 只消费展示状态，不修改状态。
- `DebugPanelPlaceholder` / `DebugSummaryPlaceholder` 只读状态，不反向驱动宠物表现。
- 调试台不得提前实现波形、时间轴、文本高亮或延迟校准。
- 不要新增第二套状态枚举；一旦创建 `PetState`，所有 UI 状态文案和测试都应引用同一模型或同一展示映射。
- 不要为此 Story 引入 ViewModel、DataStore、协程计时器或生命周期复杂度；当前单屏 Demo 可先用轻量状态 holder，后续真实播放再升级。

### Anti-Patterns

- 不要把 mock 状态入口做成正式用户流程或复杂调试控制台。
- 不要在本 Story 接入 Android `TextToSpeech`、`MediaPlayer`、`AudioRecord`、`MediaRecorder`、文件选择器、网络、数据库或真实 AI。
- 不要新增 Android 权限。
- 不要实现 7 类嘴型视觉；最多定义闭口数据状态，视觉切换属于 Story 1.4。
- 不要实现播放时间轴、波形、文本高亮或延迟校准。
- 不要用颜色作为唯一状态表达。
- 不要用自动定时器假装完成真实播放生命周期；使用显式 mock 事件保持可测试。
- 不要引入 ViewModel / coroutine / DataStore 等额外复杂度，除非确有现有依赖和明确必要性。
- 不要删除 Story 1.2 的布局和无障碍测试。
- 不要使用旧 iPadOS / SwiftUI / AVFoundation 方案；所有旧平台表述均已被 Redmi Pad SE / Android 决策覆盖。

### Latest Technical Notes

- Android 官方 Compose state 文档建议通过状态提升让 Composable 变得可复用、可测试；状态应由调用方持有，Composable 通过参数接收当前值并暴露事件。
- Android 官方 Compose architecture 文档强调单向数据流适合 Compose：UI 接收状态并发送事件，状态 holder / reducer 处理事件后产生新状态。
- Android 官方 Compose semantics 文档说明 semantics 会同时服务无障碍、自动填充和测试；本 Story 的动态状态需要进入语义树。
- Android 官方 Compose testing 文档支持通过 semantics 查找节点、断言属性并操作 UI；本 Story 应用语义和文本断言验证状态同步。
- Android 官方 Compose animation 文档支持 `animate*AsState` 和 `updateTransition`，但本 Story 不需要真实动画；Story 1.5 再引入动作动效。
